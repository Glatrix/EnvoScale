# Golden tests

An input file and its exact expected output, side by side. A test passes when the tool's
output is byte-identical to the expected file (after normalizing CRLF to LF).

| Folder | Tool | Input → expected |
|---|---|---|
| `lexer/` | `envoc0 lex` | `name.envo` → `name.tokens` |
| `parser/` | `envoc0 parse` | `name.envo` → `name.ast` |
| `check/` | `envoc0 check` | `name.envo` → `name.check` |
| `s1-parser/` | `envoc1 parse` (Envo-S1) | `name.envo` → `name.ast` |
| `eir/` | `envoc1 eir-check` | `name.eir` → `name.out` (canonical form; `name.out` must also print as itself) |
| `opt/` | `envoc eir-check -O2` | `name.eir` → `name.out` (the module after `-O2`'s EIR passes) |


## Syntax tree format

```
<2 spaces per level><node>[ <text>] @<line>:<col>
```

- One node per line, children indented below it. `node` is the node kind (`fn`,
  `binary`, `member`, …; the full list is `bootstrap/stage0/src/nodes.eas`).
- `text` is the source text of the node's token, for kinds that have one: names,
  literals and operators (`binary +`, `assign +=`, `name print`).
- `@line:col` is the position of the node's token (for `binary`, the operator).
- Each kind prints a fixed number of child slots, in order. An empty slot prints `-`,
  and a slot holding a list prints every element. For example `fn` prints
  return type, parameters, body; `for` prints init, condition, step, body.
- Parentheses do not appear in the tree.
- Envo-S1 trees (`s1-parser/`) add, after the fixed slots, the extra children a node has
  (generic parameters, interfaces, `where` clauses, origins, methods, payloads, guards),
  and print modes and markers in brackets before the position: `param this [ref] @11:18`,
  `fntype [mut] @2:5`, `match [expr] @6:19`. Envo-Core trees never have either, so they
  print exactly as under `envoc0`.

## Typed tree format (`envoc0 check`)

The same tree, with what the checker worked out appended to each line:

- expressions, `var`, `param` and `field` nodes: ` : <type>` (types are written `i32`,
  `*T`, `T[]`, `T[N]`, or a struct/enum name; aliases print as their canonical type);
- `struct`: ` size <bytes> align <bytes>`; `field`: ` offset <bytes>` before its type;
- enum `variant`, and `const`/`static` of an integer, `bool` or enum type: ` = <value>`.

Nodes the checker never types (a callee's name, the `E` in `E.V`, type nodes) carry no
annotation.

## Token dump format

```
<line>:<col> <n|s|j> <class> <text>
```

- `n` = newline before the token, `s` = whitespace or comment before it (no newline),
  `j` = joint with the previous token ([lex.flags.*]).
- `class` is `kw`, `punct`, `ident`, `int`, `float`, `char`, `string` or `eof`.
- For `kw` and `punct`, `text` comes from the compiler's kind table, so a wrong
  spelling-to-kind mapping shows up as a diff. For the rest it is the source text.

Expected files are **never** generated by the tool under test. The initial lexer
expectations were produced from the spec by an independent reference model (a separate
implementation outside the repository, written from `docs/spec/01-lexical.md`) and then
reviewed line by line. When the spec changes, update the expected files by hand and
explain why in the commit.

Inputs in `lexer/` are marked `-text` in `.gitattributes` because some depend on exact
bytes (a BOM, CRLF line endings).
